# PRD: 회원 서비스 — 로그인 / 회원가입

> **문서 버전**: 1.0
> **작성일**: 2026-05-31
> **서비스**: member-service

---

## 1. 개요

회원 서비스는 머브(MUB) 사용자의 인증과 온보딩을 담당한다. 사용자는 카카오 소셜 로그인으로 진입하고, 최초 가입자는 약관 동의 → 닉네임 → 활동 지역 → 관심사 → 관심사별 선호 옵션의 단계별 온보딩을 거쳐 회원가입을 완료한다.

비밀번호 기반 자체 회원가입은 제공하지 않으며, 인증의 진입점은 **카카오 소셜 로그인** 단일 경로다.

### 현재 구현된 기능
- 카카오 소셜 로그인 (인가 코드 방식 / 카카오 SDK 토큰 방식)
- JWT Access / Refresh 토큰 발급 및 재발급
- 신규/기존 회원 분기 (`isNewMember`)
- 단계별 온보딩 (약관 → 닉네임 → 지역 → 관심사 → 옵션) 일괄 완료 API
- 시/도·시/군/구 지역 목록 조회
- 관심사 및 관심사별 옵션 목록 조회
- 이메일/ID 기반 회원 조회 (서비스 간 연동 포함)

### 이번 스코프 (문서화 대상)
1. 카카오 로그인 — 인증 진입 및 토큰 발급
2. 약관 동의 — 필수/선택 약관 동의 처리
3. 닉네임 설정
4. 활동 지역 선택 (시/도 → 시/군/구)
5. 관심사 선택 (최대 3개)
6. 관심사별 선호 공간 옵션 선택
7. 온보딩 완료 및 회원 활성화

### 비스코프 (향후 과제)
- 가입 축하 모달의 **3회 이용권 쿠폰 발급** (member-service 미구현, 별도 혜택/쿠폰 도메인 필요)
- 닉네임 중복 검사 실시간 API (`DUPLICATE_NICKNAME` 코드만 정의됨)
- 회원 탈퇴 / 휴면 전환 플로우
- 약관 버전 관리 및 재동의 요청

---

## 2. 사용자 상태 (MemberStatus)

| 상태 | 설명 |
|------|------|
| `INACTIVE` | 카카오 로그인은 했으나 온보딩 미완료 (가입 진행 중) 또는 휴면 |
| `ACTIVE` | 온보딩 완료된 정상 회원 |
| `MUBACTIVE` | 머브 구독 회원 |
| `DELETED` | 탈퇴 회원 |

- 카카오 최초 로그인 시 회원은 `INACTIVE`로 생성된다.
- 온보딩(`/api/onboarding/complete`) 성공 시 `ACTIVE`로 전환된다.
- 이미 `ACTIVE` / `MUBACTIVE`인 회원이 온보딩을 재요청하면 `ALREADY_ONBOARDED` 오류로 거절한다.

---

## 3. 화면 플로우

```
[카카오로 시작하기]
   └─ 카카오 인증 → 토큰 발급 (isNewMember 판별)
        ├─ 기존 회원(ACTIVE) → 메인 홈
        └─ 신규 회원(INACTIVE) → 온보딩 시작
              │
   (1) 약관 동의  ── 필수 3종 + 선택 1종, "모두 동의"
   (2) 닉네임 입력 ── 2~10자
   (3) 활동 지역  ── 시/도 → 시/군/구 (바텀시트)
   (4) 관심사 선택 ── 최대 3개
   (5) 관심사별 옵션 ── 관심사별 1개 이상
              │
        └─ 온보딩 완료(ACTIVE) → 가입 축하 모달 → 메인 홈
```

프론트엔드는 단계별 화면을 순차 진행하지만, 백엔드는 모든 입력을 모아 **단일 온보딩 완료 API**(`POST /api/onboarding/complete`)로 한 번에 처리한다. 단계별 임시 저장은 클라이언트가 보관한다.

## 4. 기능 요구사항

### 4.1 카카오 로그인 (Authentication)

**목적**: 카카오 계정으로 머브에 진입하고 인증 토큰을 발급받는다.

**지원 방식**:

| 방식 | 엔드포인트 | 사용 맥락 |
|------|-----------|-----------|
| 인가 코드 (서버 리다이렉트) | `GET /api/auth/login/url` → 카카오 인증 → `POST /api/auth/login` | 웹 / 인가코드 전달 |
| 카카오 콜백 | `GET /api/auth/kakao/callback?code=` | 카카오 redirect_uri 직접 처리 |
| SDK 토큰 (네이티브) | `POST /api/auth/login/token` | 모바일 앱이 카카오 SDK로 받은 access token 전달 |
| 토큰 재발급 | `POST /api/auth/refresh` | Access Token 만료 시 |

**요구사항**:
- 카카오로부터 받은 사용자 정보(카카오 ID, 이메일)로 회원 식별.
- 기존 회원이면 로그인, 신규면 회원 레코드를 `INACTIVE`로 생성.
- 응답에 `isNewMember` 플래그를 포함하여, 프론트가 온보딩 진입 여부를 판단할 수 있게 한다.
- Access Token(Bearer) + Refresh Token을 함께 발급한다.
- Refresh Token은 서버(Redis)에 저장하여 재발급 시 검증한다.

**제약 조건**:
- 지원 소셜 제공자는 현재 `KAKAO` 단일.
- 카카오 토큰이 유효하지 않으면 `INVALID_TOKEN`(401)으로 응답.
- 카카오 API 장애 시 `EXTERNAL_API_ERROR`(500)로 응답.

---

### 4.2 약관 동의 (Terms Agreement)

**목적**: 서비스 이용에 필요한 법적 약관 동의를 수집·보관한다.

**약관 종류**:

| 약관 | 필수 여부 |
|------|-----------|
| 서비스 이용약관 동의 (`TERMS_OF_SERVICE`) | 필수 |
| 개인정보 처리방침 (`PRIVACY_POLICY`) | 필수 |
| 위치서비스 이용약관 동의 (`LOCATION_SERVICE`) | 필수 |
| 마케팅 수신 동의 (`MARKETING`) | 선택 |

**요구사항**:
- "모두 동의" 시 필수/선택 약관 모두 체크.
- 필수 약관이 하나라도 미동의면 온보딩을 진행할 수 없다 (`TERMS_AGREEMENT_REQUIRED`, 400).
- 동의 시각(`agreedAt`)을 함께 저장한다.
- 약관별 "더보기"는 각 약관의 외부 웹 페이지로 이동한다(프론트엔드 처리, 백엔드 무관).

**약관 원문 링크 (참고)**:
- 서비스 이용약관: https://www.notion.so/260365ae0b2680b9b92bd7ca2cd0084b
- 개인정보 처리방침: https://www.notion.so/260365ae0b26803596f1ceb1d9494135
- 위치서비스 이용약관: https://www.notion.so/260365ae0b2680348584de09228bac88

---

### 4.3 닉네임 설정 (Nickname)

**요구사항**:
- 디자인 기준: **2~10자**, 텍스트만 입력 가능, "다음" 버튼은 2~10자 입력 시 활성화.
- 허용 문자: 한글, 영문, 숫자 (`^[가-힣a-zA-Z0-9]+$`).
- 최대 10자 초과 입력 불가.

**구현 메모(갭)**: 현재 서버 검증은 `@NotBlank` + `@Size(max = 10)` + 문자 패턴만 적용되어 **최소 2자 제약이 누락**되어 있다 (1자도 통과). 디자인 정합을 위해 `@Size(min = 2, max = 10)`로 보강 필요. → TRD §11 참조.

---

### 4.4 활동 지역 선택 (Region)

**요구사항**:
- 시/도(`distCode1`) 선택 → 해당 시/도의 시/군/구(`distCode2`) 목록 노출.
- 지역은 가입 후 언제든 변경 가능 (디자인 안내 문구).
- 서버는 선택된 `distCode1` + `distCode2` 조합이 유효한지 검증한다 (`INVALID_DISTRICT_CODE`, 400).

**지역 목록 조회 API**:
- `GET /api/districts/code1` — 시/도 목록
- `GET /api/districts/code2?distCode1=` — 특정 시/도의 시/군/구 목록

---

### 4.5 관심사 선택 (Interests)

**관심사 종류 (9종)**:
자기계발 · 재테크/투자 · 독서/글쓰기 · 교육/멘토링 · 운동/스포츠 · 맛집/카페 · 음악/악기 · 댄스/무용/연기 · 사진/영상

**요구사항**:
- **최대 3개** 선택 가능. 1개 이상 선택 시 "다음" 활성화.
- 3개 초과 선택 시도 시 "관심사는 최대 3개까지 선택 가능해요" 안내.
- 서버는 1~3개 범위를 강제한다 (`INVALID_INTEREST_COUNT`, 400).

---

### 4.6 관심사별 선호 옵션 (Interest Options)

**목적**: 선택한 관심사별로 선호하는 공간 옵션을 수집하여 추천에 활용.

**요구사항**:
- 선택한 **관심사별로 1개 이상** 옵션 선택 시 "다음" 활성화 (`INTEREST_OPTION_REQUIRED`, 400).
- 각 옵션은 해당 관심사에 허용된 옵션 집합에 속해야 한다 (`INVALID_INTEREST_OPTION`, 400).
- 옵션은 관심사 카테고리별로 다르다 (예: 운동/스포츠 → 잔디구장·샤워·장비대여 / 음악·악기 → 방음·녹음 등).

**구현 메모(갭)**: 디자인은 관심사별 **최대 5개** 선택 제한을 명시하나, 현재 서버는 상한을 검증하지 않는다 (1개 이상만 강제). 디자인 정합을 위해 상한 검증 추가 검토. → TRD §11 참조.

**옵션 목록 조회 API**:
- `GET /api/interests` — 관심사 + 관심사별 선택 가능 옵션 전체 목록

---

### 4.7 온보딩 완료 (Onboarding Complete)

**요구사항**:
- 위 4.2~4.6의 모든 입력을 단일 요청으로 받아 처리한다.
- 처리 순서: 약관 동의 저장 → 닉네임 설정 → 지역 설정 → 관심사/옵션 저장 → 상태 `ACTIVE` 전환.
- 인증 필요: `Authorization: Bearer {accessToken}` 헤더로 식별된 회원에 대해서만 수행.
- 성공 시 `201 Created`와 함께 회원 ID·닉네임·완료 메시지 반환.
- 이미 온보딩 완료된 회원은 `ALREADY_ONBOARDED`(400)로 거절.

---

### 4.8 가입 축하 (Welcome) — 비스코프

- 디자인: "환영합니다, {닉네임}님!" 모달 + **모임활동 3회 이용권 쿠폰**.
- 현재 member-service에는 쿠폰/혜택 발급 로직이 없다. 별도 도메인(혜택/쿠폰 서비스) 또는 그룹 서비스 연동으로 추후 설계한다.
- 닉네임 표기는 온보딩 응답의 `nickname`을 그대로 사용.

## 5. 비기능 요구사항

| 항목 | 요구사항 |
|------|---------|
| 인증 방식 | JWT (Access/Refresh), Refresh Token은 Redis 저장 |
| 소셜 제공자 | 카카오 (OAuth 2.0 인가 코드 / SDK 토큰) |
| 세션 | Stateless (서버 세션 미사용) |
| 클라이언트 | 웹(localhost:3000), 모바일(Capacitor/Ionic) — CORS 허용 |
| 언어 정책 | 로그 영어, 클라이언트 응답 메시지 한글 |
| 응답 속도 | 로그인 ≤ 1s(외부 API 포함), 목록 조회 ≤ 300ms (p95) |
| 커버리지 | 서비스 ≥ 75%, 컨트롤러 슬라이스 ≥ 75% |

## 6. 에러 응답 정책 (요약)

| 상황 | 코드 | HTTP |
|------|------|------|
| 카카오 토큰 무효 | `INVALID_TOKEN` | 401 |
| 인가 코드 무효 | `INVALID_TOKEN_VALUE` | 400 |
| 카카오 API 오류 | `EXTERNAL_API_ERROR` | 500 |
| 회원 없음 | `MEMBER_NOT_FOUND` | 404 |
| 이미 온보딩 완료 | `ALREADY_ONBOARDED` | 400 |
| 필수 약관 미동의 | `TERMS_AGREEMENT_REQUIRED` | 400 |
| 관심사 개수 위반 | `INVALID_INTEREST_COUNT` | 400 |
| 관심사 옵션 누락 | `INTEREST_OPTION_REQUIRED` | 400 |
| 유효하지 않은 옵션 | `INVALID_INTEREST_OPTION` | 400 |
| 유효하지 않은 지역 코드 | `INVALID_DISTRICT_CODE` | 400 |

> 상세 필드/DTO/도메인 설계는 `TRD.md` 참조.
